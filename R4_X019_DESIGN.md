# R4 — X-019: Восемь способностей, различимость и потеря исходов при удалении каждой

**Дорожная карта:** R4 (Перенос расширенного проекта)
**Источник:** rc7, строки 442, 503; статья 79 (восемь способностей); статья 16 (признак основательности и M(x)); статья 80 (состав способности).
**Цель порта:** каждая из восьми способностей имеет точку принуждения в коде v4.1 и опыт удаления, подтверждающий потерю собственного класса исходов (M(x) > 0).

## 2. Опыт удаления X-019 — дизайн

**Принцип (статья 16):** M(x) > 0 — класс исходов, который теряется при удалении x и не восстанавливается остальными семью при тех же исходных знаниях, запасах, вычислительном запасе и признаках равенства.

**Метод опыта:** для каждой из восьми способностей C1…C8:
1. Зафиксировать baseline-сценарий, в котором все 8 способностей задействованы (сквозной сценарий статьи 78 подходит, но для X-019 достаточно локального сценария на 1–2 перехода).
2. Подменить точку принуждения Cn на no-op (в `mutation_lab` режиме, не ломая остальные 7) — то есть заглушить модуль или метод, который реализует Cn.
3. Прогнать тот же baseline-сценарий.
4. Зафиксировать класс исходов, который пропал.
5. Проверить: остальные 7 способностей не восстанавливают этот класс.
6. Восстановить Cn, прогнать baseline снова — исходы возвращаются.

**Подмодули опыта X-019:**

| Подопыт | Удалённая способность | Заглушка | Ожидаемая потеря (M(x)) |
|---|---|---|---|
| X-019.1 | C1 Познание | `Space.digest` → возвращает константу; `Observer.diff` → возвращает () | ATTEST не может проверить delta_matches_intent; V3 недостижим; все переходы блокируются на NOT_VERIFIED |
| X-019.2 | C2 Открытие | DISCOVER режим в kernel → все запросы с режимом DISCOVER отклоняются | нельзя подать переход, не описанный заранее в грамматике; новые возможности неоткрываемы |
| X-019.3 | C3 Назначение | `TransitionRequest.intent` → игнорируется; `Possibility.purpose` → None | AUTHORITY не сопоставляет цель с полномочием; переназначение непроверяемо (X-020 падает) |
| X-019.4 | C4 Созидание | GENERATE режим → отклоняется; ADD_OBJECT_TYPE/ADD_RULE effects → no-op | нельзя породить новый тип/правило; SCHEMA_ADMIT некуда допускать |
| X-019.5 | C5 Организация | `Grammar` formation_rules → пустое множество; multi-effect переходы → первый эффект | нельзя собрать структуру; многоэффектные переходы теряют связность |
| X-019.6 | C6 Наделение полномочиями | `CapabilityStack` → всегда возвращает no-capability; AUTHORIZE стадия → DENIED | G1 AUTHORITY не работает; никакой переход не авторизуется; делегирование невозможно |
| X-019.7 | C7 Исполнение и контроль | `governed_transition` EXECUTE стадия → SKIPPED; Observer → None | эффект не применяется; нет свидетельства; V3 недостижим; Budget не списывает |
| X-019.8 | C8 Сохранение и преобразование | `ActivationRegistry` → отдаёт DENIED_CONFLICT всегда; `Trace` → не пишет; `Constitution` amendments → M3 не работает | CAS по HEAD (G7) ломается; хеш-цепочка трассы пуста; поправки действуют назад |

**Критерий PASS для каждого подопыта:**
- При заглушенной Cn: класс исходов M(Cn) действительно потерян (переход не проходит или не производит ожидаемого класса результата).
- При восстановленной Cn: класс исходов возвращается.
- Ни одна из остальных 7 способностей не восстанавливает M(Cn) при заглушенной Cn (контрольная проверка: заглушить Cn, одновременно активировать все остальные — M(Cn) всё равно потерян).

## 3. Реализация в v4.1

**Расположение:** `singulyar_host/experiments/h019_capabilities_removal.py` (дополнение к существующему `h019_staged_activation.py`, либо отдельный файл `h019b_capabilities_removal.py`, чтобы не конфликтовать).

**Зависимости:** `mutation_lab` режим GovernanceStack (уже есть для лабораторных снятий гарантий G1–G7); расширяется для снятия способностей C1–C8.

**Связь с H-017 (семь порук):** X-019 — это «семь порук плюс восьмая» (или, точнее, ОСЬ способностей, не сводимая к ОСИ порук). H-017 уже доказал несводимость семи порук (матрица 7×7 диагональна). X-019 доказывает несводимость восьми способностей. Эти две оси ортогональны: поруки — про принципы управления; способности — про функции деятеля.

**Связь с H-018 (выводимость без скрытых кирпичей):** H-018 проверяет, что все построения выводимы из частей статьи 2 (SUBJECT, TRANSITION, GOVERNANCE SURFACE, SPACE). X-019 проверяет, что восемь функциональных способностей — не лишние: каждая имеет M(x) > 0.

## 4. Что НЕ покрывает X-019 (честно)

- **Полнота восьми.** X-019 доказывает минимальность (каждая из 8 необходима), но не полноту (не доказано, что этих 8 достаточно для всех родов поведения Хозяина). Полнота снята с доказательного поля решением Хозяина (статья 70, закрытие 3).
- **Выводимость из частей статьи 2.** Не доказана и не требуется (статья 79 закрепляет способности как верхний уровень описания).
- **Универсальность для всех возможных исполнений.** M(x) вынесен как приговор с областью (статья 68); значимое изменение устройства пересчитывает M(x).

## 6. Открытые вопросы для Хозяина (R7)

- **C3 (Назначение) vs G1 (AUTHORITY):** способность «Назначение» и гарантия «AUTHORITY» перекрываются в коде (intent + capability). Это одно и то же или две оси? Предварительно: способность — про функцию (определить цель); гарантия — про принцип (переход допустим только при полномочии). Требует отдельной проверки (R7 → опыт).
- **C7 (Исполнение и контроль) vs G2 (EXECUTION_BINDING) + G3 (EVIDENCE):** аналогично. Способность — про функцию (осуществлять + контролировать); гарантии — про принципы (привязка + независимость). Ортогональны, но перекрываются в коде.
- **C8 (Сохранение и преобразование) vs G7 (ACTIVATION) + M3 (поправки только вперёд):** способность — про функцию (непрерывность + восстановление + самоизменение); гарантия — про принцип (один HEAD); мета-статья — про правило (поправки вперёд). Ортогональны, перекрытие в коде.

Эти три перекрытия — кандидаты на R7 (сформулировать проверяемые гипотезы и опыты, различающие оси).
